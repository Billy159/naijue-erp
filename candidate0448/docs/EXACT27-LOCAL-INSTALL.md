# Runtime 27 local installation and startup

This is a deployment handoff, not proof that a target has been installed or tested. Use a newly provisioned, independently verified synthetic PostgreSQL database first. Never point fixture setup at retained or production data. Review every migration and permission change before applying it; a user approval to run tests is not permission to install persistent grants on a different target.

1. Install the existing reviewed schema 1–27 and standard 27 initialization on the isolated target. Provision the login account and its existing membership in `erp_unified27_runtime_2393dbc6db9581c2` using the deployment's approved account workflow. The runtime role is NOLOGIN. Do not make it an owner, superuser, or BYPASSRLS role.
2. Review and apply `adapters/postgres/patches/0027_document_specification_barcodes_successor.sql` on the target. It checks the original guard bodies before replacement. For barcode creation, separately review and apply `adapters/postgres/patches/0027_document_specification_barcodes_permissions.psql` with the explicitly selected existing runtime role. Its exact grants are visible in that file. Neither file is applied automatically by the application.
3. Check that the runtime has the SKU INSERT and product version UPDATE privileges needed for document specification creation, plus the barcode INSERT columns only when codes can be generated. `tests/integration/document-barcode-successor/admission-readonly.psql` checks guard/trigger and effective column privileges. A failed check is a stop, not an instruction to bypass a trigger or use an owner fallback.
4. Configure the existing private production runtime JSON as the normal host requires, using `profile: "source-confirmed-native-exact27-v1"` and `documentCommands: "NATIVE_RUNTIME"`. The private file must be a canonical absolute path, regular, owner-only and at most 64 KiB. Configure actual connection details and the existing explicit capacity resource in that file; no defaults or credentials belong in source control.
5. Start the backend with Node 24.21.0:

   `node apps/api/src/production-main.ts --exact27 /absolute/private/runtime.json`

   This is an explicit selector; existing exact26 selectors remain separate. The startup checks the configured database, login and runtime role, migration registry, RLS presence and transaction settings. A refused startup must not be retried using an owner account or by disabling guards.
6. In the separately deployed frontend runtime configuration, set `routes.documentListProfile` to `"source-confirmed-ordinary-documents-v1"` for the ordinary 27 sales/transfer list protocol. Configure only routes actually installed by the backend.
7. Before any real rollout, run the package's application and database tests against an isolated synthetic target and independently review results. The current real-PG runner under `tests/integration/document-barcode-successor/` still requires a fixture adapter that prepares the synthetic parent transaction and roles; it is not yet a self-contained acceptance test. Do not label it passed until that missing fixture is supplied and all forced constraints and rollback checks succeed.

Known limitations: the document append guard currently permits at most 200 newly created SKU rows per product operation; requests beyond that stop before writing, with no truncation. The exact27 issuer has not yet independently validated the full policy expressions or every installed guard, and no real-PG end-to-end acceptance is recorded for this successor. The ordinary sales settlement-statistics branch is not yet implemented. Historical source data is not needed for ordinary catalogue reads and must not be copied into the synthetic target.
