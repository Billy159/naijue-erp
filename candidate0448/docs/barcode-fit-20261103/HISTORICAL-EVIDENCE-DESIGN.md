# Historical barcode generation evidence: pending implementation

The current normal product schema does not expose the full historical product segment or per-scheme color/size codes. Existing historical barcode strings and SKU bindings are not evidence that a product segment can be recovered by slicing them. The local source snapshot reader lists `tplus_product_barcode`, `barcode_encoding_mapping`, and scheme segment/version sources; presence in that list is not evidence that a particular mapping exists or is approved.

A possible additive successor is a nullable, versioned product JSONB evidence field. Its entries would bind the exact product ID, scheme ID, color ID, fit ID and size ID to the full raw product segment and explicitly sourced historical color/size strings, and each value to a source file SHA-256 and precise source-row identity. Unique `(scheme, color, fit, size)` keys, bounded lengths/count, exact raw strings, explicit null/error on gaps, no duplicate/conflicting entries and no guessed defaults are required. The 2021-fit segment remains intact and must not be split or receive a second fit suffix.

This is a design, not a supported input or installed schema. Hash syntax alone does not authenticate a value. A safe implementation must validate supplied mappings against actual pinned source records and user-approved local cleaning decisions, or explicitly mark them as local attestation rather than independent source proof. Only an existing specifically authorized import path should write them; ordinary product editing must not mint or overwrite evidence. Existing import/receipt/audit guards need explicit typed handling, including update of an already retained product, immutable conflict detection, permission checks and rollback. Additive JSON must be represented by a new exact schema-declaration profile; old V1 remains readable with its old hash. A provenance mapping existing in a source system does not mean it has been copied or accepted in this target.

Adding a nullable product column alone is **not compatible** with the current SQL path. The standard importer checks source field names against every physical product attribute, so an old V1 row omitting that column fails its exact-fields guard. The product CREATE audit guard also checks each resulting root field against the request audit; an absent new field breaks old CREATE even when the stored value is null. A successor must explicitly handle both boundaries and their row-equality/receipt proofs, with versioned catalog pins and tests for old V1 and new evidence. `standard_import_row_intent` populating an absent field as null does not bypass the earlier exact-fields guard. No deployed behavior is implied by the declaration-only validator.

No SQL, schema, permissions or actual product data are changed by this document. Until the full source-verifying import route, constraints and tests exist, historical generation requiring this unavailable data must fail explicitly for affected SKUs. Other well-supported schemes/SKUs should continue; no full-database re-generation or implicit resurrection.

Before enabling the successor, isolated PostgreSQL verification must prove all of the following against the same pinned catalog: unchanged V1 import and product CREATE/EDIT behavior; successful, audited writes only through the restricted successor; rejection of ordinary product API evidence injection, unknown keys, spoofed source pins, duplicate or conflicting coordinates and any overwrite; complete rollback on faults; and exact pre/post identity and binding checks for fit, SKU and historical barcode. Test the new-SKU path using the real product/scheme/color/fit/size coordinate resolved to the actual SKU in the same transaction. Tests using local declarations must label them as such and must not claim the database verified the source bytes. Preserve the failed runs and record the exact SQLSTATE, commit/rollback acknowledgement and resulting catalog fingerprints.

New SKU identifiers may not exist until the controlled product transaction. Evidence identifies product/scheme/color/fit/size; only the actual transaction may bind that exact coordinate to its newly allocated SKU. No caller-provided SKU is invented and the 2021-fit source product segment is not split.
