# v0.3 填写补充说明：收款账户与历史来源推荐厅关系

本说明只澄清开发侧模板的含义，不要求重新整理账户，不修改、删除已填写的关系，
也不恢复已暂停的真实数据处理。原 v0.3 页签、表头和已填内容保持兼容。
本次没有重生成 Excel，没有修改任何原件或资金业务记录。

## 正常账户是否可选

按已核当前线上运行逻辑：所有状态正常、对应收款方式启用且匹配当前方式的账户，
都可以选择。账户是否出现在某厅的推荐关系中，不是可选资格的条件。

本厅最近有效已审核销货中每种方式的合格账户，与旧来源 sourceFacts.hallIds
所保留的厅推荐关系合并形成推荐，仅用于置顶。未被推荐的合格账户仍然可选。
具体“最近”的时间/顺序、并列处理和运行时排序由对应已核实现确定，不能由填表人
或离线预检另猜一套。

## “11账户适用厅”应怎样理解

该页签保留旧名称只是为了兼容，实际含义是：

- 历史来源推荐关系，可选，不是账户或营业员权限。
- 可以整页留空，也可以暂不提供，不要求每个账户都填一行或绑定一个厅。
- 未提供不限制全体正常且方式合格的账户可选，不是缺少必需业务主数据。
- 不要求人工重新分配账户；已经填写的真实旧关系原样保留，不删除、不改写。
- 两个原表头“*账户来源编号”“*厅来源编号”不变。星号表示确实提供一条历史
  推荐关系时，该行两个来源键应能定位；不表示必须新增关系或补造权限。
- 已提供关系如有无法核对的引用，只报告该来源关系本身的问题，不把其他正常
  账户排除，也不把该关系改造成权限授权。

账户维护 UI 和列表没有“适用厅”输入，不应要求在维护流程重新勾选厅；详情中的
来源厅范围只读，用于展示旧来源事实。

## 离线预检边界

开发侧预检允许“11账户适用厅”为空或未交，在 STAGED 和 FINAL 模式都不会仅因
该页未提供而报必需页缺失、账户权限缺失或营业员权限缺失。

若有真实旧关系，仍保留原来源键和引用检查，不能借此修改账户、员工权限或
实际资金记录。预检不生成权限，不执行正式导入，不决定最近账户排序，不连接
数据库。正式写入、来源事实承载及运行时接线另按已核合同验证。

## 已同意补充的唯一来源事实：原收款方式编号快照

已批准的目标是在现有收退款明细表 sales_settlement 中补充唯一字段
payment_method_id_snapshot，用来保留该条原记录当时的收款方式编号。
这不是新增表，也不是新增账户或营业员权限。

原“15历史收退记录”的八列完全兼容，无需重填：

1. *来源编号
2. *单据来源编号
3. *原收退行号
4. *账户来源编号
5. *方向
6. *金额
7. 原账户显示名
8. 原方式显示名

如原记录本来就有当时的方式编号，可以在这八列末尾可选追加第九列
“原收款方式来源编号”，由开发通过“09收款方式”的来源身份映射到上述唯一字段。
不要求为了该字段重新清洗无关数据或重填原八列。

“原方式显示名”不是编号；账户今天所属的方式也不证明原记录当时的方式。
开发不能用名称匹配或当前账户反推补值。旧表未提供、来源没有或确实未知时，
保留未知/null，历史资料可以保真保留，但该未知事实不能生成最近账户推荐。
明确填写的编号若暂缺后批映射，只定位到该原记录及字段待核，不造新编号。

历史值优先由程序从原记录提取；也可以由开发整理有原件依据、按原收退记录来源键
关联的受控补充映射，无需改写原表。本轮仅接通可选追加列的离线读取合同，尚未
实现补充映射加载或自动补齐，不声称已执行历史回填。新的运行时收退款记录则由
服务端捕获已知的当前方式快照。实际保存及推荐算法由对应后端实现核验。提供了方式编号，也不等于该历史记录已经可以
参与推荐；仍须有效已审核历史、有效贡献承接及当前账户/方式合格组合等条件通过核验，
不能由离线预检越过尚未完成的历史能力门禁。

本次只修改开发侧说明和合同，没有读取、处理或修改已暂停的真实数据。
