# 商品组内完整尺码：收窄后的剩余保存方案 v2

当前已确定的业务范围：商品真实所属尺码组是硬边界。该组完整有效成员（含缺 SKU 的 XS、XL 等）必须能选择和输入；其他组裤码、无尺码不能混入，无尺码仅本组有此成员时可选。服务端保存时重读当前商品组及真实成员关系，不能只信前端。已有历史 ID、编码、条码、规格和快照保留；历史回显不产生新增跨组资格。这些方向不再询问。

原“商品组仅默认展示、所有组均可新增”的 v1 已被人类最新纠正覆盖，旧批准只保留历史，不能执行。D1/D2/D3 未实施这部分生产规则，原成员和权限校验保持；D2 曾写的一条跨组 RED 草稿已原位保全并标注 superseded/skip，未删除或冒充当前目标。

能直接推进的部分继续：读取真实商品 sizeGroupId 后，展示本组完整字典成员，不能只显示已有 SKU。零 SKU 商品也由商品自身读组，缺失或读取失败报错，不回全局组。已有合法 SKU 继续原 draft/prepare/SAVE、版本、权限和幂等链路；C180 的只读三文件独立有效。

剩余问题只在“组内确实没有 SKU 的格子怎样保存”。推荐一套待确认的窄规则：

1. 在原 SAVE 同一事务内，以商品、颜色、版型、尺码 ID 查真实四维 SKU；重读并锁定商品当前尺码组和成员。已有则复用原 ID、原编码；本组缺少才补建，仅补本单非零实际使用的规格。读取、准备、取消均不建档。停用对象不自动恢复。
2. 本次新补规格编号明确采用 `NJNEW-` 加新 SKU UUID 去横线的32位小写字符，共38字符，标注“新系统补规格编号”，不称原码、不是条码。所有已有/导入/人工编码逐字保留；本规则不回填历史缺码。唯一冲突整笔回滚，不猜号或替换旧身份。原系统没有可直接复用的业务编号分配器，所以这一新规则仍待确认。
3. 营业员只获得为当前已获准保存的单据补本组规格的受托权，不能通用编辑商品、改价、改组、启停、删除或借用管理员。每个实际新增规格的商品沿原 PRODUCT EDIT 记录商品版本+1、新 SKU v1/创建操作/稀疏审计和回执，其他主档不变；和单据同提交、同回滚。普通商品维护原权限保持。
4. 如果新真实 SKU 没有启用 MAIN 条码，建议手工录入可用：原事务确认实际没有 MAIN 后保存真实空条码。缺 SKU、读取失败或资格未知仍拒绝。扫码仍要求真实、有效、唯一的绑定，原码不重算、不补假主码。此手工无 MAIN 语义仍待确认。
5. 原两个 commands 的 SAVE 仅增加互斥 proposal 分支：选择传真实 skuId，或传 spec:{productId,colorId,fitId,sizeId}。不需要 client groupId，服务端自己核真实所属组。旧 draft 内容、幂等哈希及结果保持；新分支按原请求键、当前权限和版本锁运行。原明细身份、未改历史快照、符号、单位、金额、库存0影响及未知提交恢复不变。

上述同事务补建还需明确的依赖实现：先核完整已提交商品基线，再只认可本次获准 SAVE 实际追加的 PRODUCT 操作；不把任意未提交/STAGED 行放行。延迟校验须核同 actor、同事务、真实父 SAVE/未审核单据及新增 SKU 实际用于本单，单看内部请求键前缀不能授权。该依赖和上面新编号、受托权、无 MAIN 规则一起提交确认，不先实施。

收窄后的候选影响是22个生产文件（D1=19、D2=3、D3=0），从旧29件逐件剔除7件；并非继续批准旧29。商品组字段、成员限制、库存准入函数及投影不改。拟 SQL 仅替换原 actor/原生创建两函数，新增一个父单目的闭包函数和一个延迟约束触发器；新增表、列、序列、FK、action、target和公开URL均0。原迁移不重写；C统一确认及精确登记后才可实施/隔离验证。

只需就上述“组内缺 SKU 保存”的新写入规则作一次确认，不再问已确定的所属组范围。当前这22件候选没有实施或数据库验证。原 v10 实现 bug 修复、C180只读输出、UI和合法 SKU 继续；B07 已批原行数量/金额修订是另一独立范围，不把厅仓/SKU/账户/方向/状态/人员时间或增删行夹入。
