# Source-review v1 wire frozen with the SQL owner

This is a separate unresolved-source protocol, not the existing f5d hall profile. No department, ordinary target, warehouse UUID, accounting cutoff or confirmed historical hall is synthesized. Only capture record UUIDs are deterministic identities. Fresh bootstrap, execution admission, durable SQL capture and eventual conversion/reprocessing are separate gates; this application/CLI implementation does not complete them.

Approval JSON has exactly format_version=`HISTORICAL_SALES_SOURCE_REVIEW_APPROVAL_V1`, source_namespace, package_manifest_sha256, records. Each record has exactly the fields in `SourceReviewRecord` in packages/application/src/historical-sales-source-review.ts. source_ref has file_sha256, sheet (string/null), row (positive bounded int), occurrence (nonnegative bounded int). raw_fields preserve strings/null; missing properties stay missing. normalized_fields/null and normalization_version/null are paired. Reliable original hall evidence is preserved text/null, not an inferred current UUID. reason is WAREHOUSE_UNRESOLVED. grouping is COMPLETE_GROUP, ORPHAN or AMBIGUOUS. COMPLETE_GROUP requires one matching original header; unbound/ambiguous groups are not guessed.

Occurrence hash is SHA256 of exact UTF-8 JSON.stringify([namespace,entity,file_sha256,sheet,row,occurrence]). Capture ID is first 32 hex digits made an RFC 9562 UUID v8 by replacing hex index12 with 8 and index16 with (original & 3) | 8. No ordinary business ID is generated. Source hash preimage is the 15-item ordered tuple returned by sourceReviewRecordPreimage. Its raw UTF-8 is hashed, persisted and compared as parsed JSON; SQL must not substitute jsonb::text or accept duplicate JSON keys. Original approval bytes are retained separately without reserialization.

Capture wrapper: id, occurrence_key, source_record_sha256, source_hash_preimage, source. All are derived from a genuine externally SHA-pinned approval capability. A clone/plain object is not a capability. Bounds: approval 64 MiB/250000 occurrences, preimage 1 MiB/occurrence, segment 1 MiB, payload 1000 records and below 8 MiB with 64 KiB reserved for the command envelope, under BOTH compact JSON wire and structurally exact PostgreSQL jsonb::text UTF-8 lengths. projectedJsonbTextBytes counts one space after object colons and structural commas, never punctuation inside strings; key order does not affect length. The helper supports the protocol JSON domain with finite safe integers and rejects getters, cycles and unsupported values. NUL and lone surrogates are rejected with no mutation, not normalized for PostgreSQL.

SQL owner confirmed command exact keys:
- protocol=`HISTORICAL_SALES_SOURCE_REVIEW_SQL_V1`, operation_id, request_key, batch_id, expected_sequence, source_namespace, package_manifest_sha256, approval_sha256, phase, payload.
- REVIEW_STAGE payload: source_manifest_ref, approval_bytes, expected={occurrences,headers,lines,settlements,known_groups,ungrouped_occurrences}. STAGE expects/stores sequence0.
- REVIEW_APPROVAL payload: offset, bytes_base64. Decode canonical base64 <=1MiB; offsets are contiguous and full bytes verify external hash/UTF-8/unique JSON keys before capture. Every subsequent committed phase advances sequence by1.
- REVIEW_CAPTURE payload: records (capture wrappers above).
- REVIEW_SEAL payload: empty object. Verify complete occurrence-set equality, counts and grouping; no ordinary or ledger effect. PASSED is complete capture, not IMPORTED.
- REVIEW_RESOLVE: explicit NOT_IMPLEMENTED rejection in this first candidate. No REVIEWED_READY/MATERIALIZED promise or invented successful review decision. Conversion and atomic source consumption require the separate reviewed successor.

Read exact keys: protocol, batch_id, source_namespace, package_manifest_sha256, approval_sha256, after_occurrence_key (null/string), limit (1..100). Session token is a separate API argument and never source/audit/request-hash data. SQL API admission requires existing current ADMIN, protected importer, fixed SECURITY DEFINER/ACL/RLS checks described in the design; no application object is a substitute.

The application helpers produce summaries, exact approval byte segments and capture payloads, not executable commands. The standalone CLI requires --offline, --package, --manifest-sha256, --approval, --approval-sha256, with realpath-confirmed approval outside the package. It prints only count/hash metadata and explicit source_files_read=false, persisted=false, database_connected=false, fresh_bootstrap_closed=false, reprocessing_implemented=false. It verifies the pinned manifest and approval, but does not read source workbooks or claim complete source-to-target census. No connection URL, host dispatch or existing importer fallback is accepted.

Original number lexemes are checked after strict duplicate-key parsing, using Node24 JSON.parse reviver context.source. Coordinates must be exact mathematical nonnegative integers within int32, not numbers that only become integral after IEEE754 rounding. Decimal/exponent representations such as 1.0, 0.0 and 0.1e1 remain accepted and hash canonically as integers, while original approval bytes are kept exactly. PostgreSQL numeric digit/scale bounds are checked without materializing giant powers. Raw field strings are not interpreted as numbers. Older engines without lexical context fail closed rather than silently rounding.
