## 接收边界

初始化请求新增可选 `historical_line_amount_approval: { utf8, sha256 }`，仅允许本轮新的显式历史厅来源 profile。既有 profile 不能通过该字段获得金额例外。它承载与离线证据相同的 `HISTORICAL_LINE_AMOUNT_EVIDENCE_V1` 原始核查字节，最大 4 MiB、最多 10,000 行，而不是“六条例外”开关。

初始化检查严格 JSON 唯一键、外层 SHA、来源命名空间、封闭字段集合、UUID、规范精确数字字符串、原数量非零、确有金额差异，以及父/子来源定位、明细身份与来源发生位置不重复。证据行一次按明细 ID 建立查找表，后续分块不能更换原始初始化核查。

每个差异明细必须匹配：

- 原父单 ID、来源键、来源文件/工作表/行集合；
- 原明细 ID、来源键、来源文件/工作表/行集合；
- 原数量、原成交单价、原金额三个字符串；
- 同一文档批次、明确的 `CUTOFF_HISTORY` 和新的 profile。

客户端明细不允许自行携带金额例外字段。SQL 从初始化中已绑定的核查构造 `HISTORICAL_LINE_AMOUNT_BOUND_V1`，把核查 SHA、来源 SHA、完整事实一起纳入逐行 `source_record_hash` 以及不可变导入审计。发布时要求每个核查事实恰好出现一次；缺条、多条或改值均不能完整发布。

**SHA 绑定核查字节，不证明原始业务事实真实。** 受信任宿主仍须将包外独立审阅的 SHA 与核查字节绑定，来源负责人仍须核查真实原文件。不能允许包自己给出核查和自算 SHA 后便称为独立批准。现执行编译器仍阻断金额差异，尚未接入该宿主批准流程。

## 持久化及读回

原数量、原单价、原金额继续分别写入原有独立列，不改算、不凑平、不新增补差行。迁移提交校验再次绑定已提交初始化回执、批次、命名空间、父子来源 proof、原值及持久化逐行摘要。已知行金额合计与原头毛额、净额、完整已知优惠分摊仍须一致；已审核单有原收退记录时仍须核对净收退，空原收退集保持原有未知语义。

既有 `standard_whole_package_verify_v2` 的凭证、角色、锁、原始快照及后续版本链校验保持不变。返回新增 `historical_line_amount_differences`，分列给出：

- 原数量、原单价、原金额；
- 另算的理论金额及“原金额 − 理论金额”；
- 当前三个值及是否仍与原值一致；
- 来源定位、独立核查 SHA 及原始事实证据。

全部运算用 SQL `numeric`，全部金额/数量输出文本，不经过 JavaScript Number。理论金额和差额只供诊断，不覆盖原金额。读回是现有导入核验入口的受限输出，**不是已完成的原生表单展示或普通用户新权限**。

## 组合独审后的恢复摘要修复

独立审查发现：既有无结算原样恢复校验只用 `source_key / fields / source_refs` 重建来源摘要，遗漏新 profile 导入时已写入的 `historical_hall_evidence`。这会把合法的原始证据误判为 `RESTORATION_SOURCE_INVALID`。新增专项先红测试已复现源摘要输入不一致，随后修复；这是源码与离线摘要输入模型验证，不是 PostgreSQL 实测。

修复只对已验证原始初始化明确选择的新 profile 生效。恢复校验保留初始化 root，并要求每条源审计属于该 root；`explicit_zero_evidence / zero_amount_archive / historical_hall_evidence` 按原导入摘要合同加入，且必须与原请求具有完全相同的存在性和值。证据类型、所属实体、显式零的数量也再次检查。新 profile 的销售头仍必须带原厅证据。金额差异仍不允许借原样恢复重新审核。

旧 profile 保持原三字段摘要合同，没有借此扩宽。只读源路径审查还发现旧 profile 的 zero/archive 生产端也会加入扩展，而原恢复端没有加入，存在同类摘要不一致风险。已补合成摘要输入反例，但未连接数据库证明完整执行路径；此旧路径问题仍待单独评审，不宣称已解决或旧路径全部通过。
