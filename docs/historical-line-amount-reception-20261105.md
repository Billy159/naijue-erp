# 历史原单价、数量、原金额差异：接收合同与边界

状态：**离线源码候选，未接入数据库执行**。本说明和测试只用合成数据。没有读取用户的六条原始记录，没有连接 PostgreSQL，没有安装迁移、改生产数据或推送部署。

## 本轮已实现

`readHistoricalLineAmountEvidence` 读取单独提供的来源核查文件，调用方必须另外提供受信任 SHA256。核查文件不能放在待接收包内，不能由包自己给一个 `allow` 标志放行。

每条核查记录绑定：

- 来源命名空间、被核查原文件 SHA256；
- 父单来源键、父单目标 ID、父单原文件/工作表/行位置；
- 明细来源键、明细目标 ID、明细原文件/工作表/行位置；
- **原数量、原两位单价、原两位金额三个字符串**。

核查文件 SHA 校验只是确保使用已审阅的那份字节，不代表程序自行证实原始业务事实。原始事实仍须来源核查负责人依据原文件核实。实现只接受精确完整集合，不用“容差”“按金额猜单价”或“仅六行例外”开关。

普通完整包预检和流式预检共享同一证据校验。只有来源绑定的历史 `CUTOFF_HISTORY` 单据能够使用该例外，新建运行单据不能借用。无证据、复制出的普通对象、源位置或父单变更、数量/单价/金额任一变更、错 SHA、缺条、多条和重复条都失败关闭。

预检不改源记录。原金额继续参与原单头合计和原收退核对，已知单头金额矛盾、收退金额矛盾仍然阻断。

## 离线持久化和读回

流式预检保存：

- `index.sqlite`：原包的字段与来源定位，仍是私有离线索引，不是业务数据库。
- `historical-line-amount-evidence.json`：精确原核查字节，保留单独给定的 SHA。
- `historical-line-amount-differences.jsonl`：逐行原数量、原单价、原金额，以及另外列出的理论金额和差额。
- `summary.json`：索引、差异文件和核查文件的 SHA/字节数，以及差异行数。差异结果标明 `OFFLINE_ARCHIVE_ONLY`。

差额定义为“原金额 − 原数量 × 原单价”。所有运算用整数最小单位和任意精度整数；理论金额和差额只用于诊断，**不替换原金额**。大于 JavaScript 安全整数的原值也保持精确。

实际离线 CLI：

```sh
node tools/unified-import/cli.mjs stream-preflight \
  --package <合成标准包目录> --report <新报告目录> \
  --manifest-sha256 <独立清单SHA> --allow-synthetic \
  --historical-line-amount-evidence <包外核查文件> \
  --historical-line-amount-evidence-sha256 <独立核查SHA>
```

此入口不会生成可执行数据库写入授权。普通执行计划仍拒绝这些差异；流式计划和直接明细请求生成器还会再次检查实际明细，不能通过删掉摘要中的差异标记绕过。

### 同一包同时包含营业厅推定与原金额差异

普通目录 CLI 也已在 `validate --offline` 分支接入相同的包外读取器。带核查文件时必须同时指定独立清单 SHA，不能省略 `--offline`，不能把核查文件放回待检包内，也不能由程序自行计算一个 SHA 当作真实业务核查授权：

```sh
node tools/unified-import/cli.mjs validate --offline \
  --package <合成标准包目录> --report <新报告目录> \
  --manifest-sha256 <独立清单SHA> --allow-synthetic \
  --historical-hall-approval <包外厅依据核查文件> \
  --historical-hall-approval-sha256 <独立厅核查SHA> \
  --historical-line-amount-evidence <包外金额核查文件> \
  --historical-line-amount-evidence-sha256 <独立金额核查SHA>
```

将 `validate --offline` 换成 `stream-preflight` 即为同一包的流式离线命令。两个入口使用同一新厅证据 profile `f5d4e26d8cfae8cc96d42a43b01c6c49217a9927d1b0dc42af0c1b4c3ce29b66`，要求全部历史销售头的厅依据由同一完整 bundle 覆盖。原始厅未知、仓厅可确认时显示迁移派生；两者无法确认时保持待核。六行金额三项原值分别保留。

导出时间未知时，两入口还接受 `--current-effective-alignment FILE --current-effective-alignment-sha256 SHA`，保持原 `exported_at=null`，并绑定库存原文件、截止时间、registry 和全部当前单据文件。不带这份核查仍失败关闭。

新增组合测试使用**同一个合成包**运行真实普通和 stream CLI，比较差异读回、SQLite 中的原三项数值和厅依据，并检查原包字节未改变。负例同时运行两个 CLI：缺任一 bundle、错/缺 SHA、包内自证、改原单价、改取值时仓版本、去掉厅证据、降回旧 profile、清单 pin 不同及未知导出时间缺核查。另检查普通 CLI 不接受重复选项、隐式在线模式或数据库参数。

这里的 SHA 由测试夹具计算，只为检验传递和篡改拒绝，**不是独立业务信任来源**。本节接线仅属于离线预检；实际 host/compiler 的本批执行能力仍未接通，SQL 源码候选也不能替代安装及 PostgreSQL 验收。不得将“两个 CLI 通过”描述成“已能导入并保存审核”。

## 数据库存储的最小后续方案

现有 `sales_line.quantity`、`deal_price`、`line_amount` 是独立列，现有 sealed migration snapshot 和解码器也分别读它们。新增合成协议测试已证明解码器不会重算原金额；**这不是 PostgreSQL 写入和读回验收**。

要将本轮离线方案接入真实业务存储，至少还需：

1. 在版本化导入初始回执中绑定独立核查文件 SHA 和完整逐行集合；在不可变 `import_record` / 迁移审计中保留原值及原文件行定位。
2. SQL 接收端再次核对命名空间、父子 ID、完整集合、精确原值、源定位和回执链，不仅信任客户端预检或 `CUTOFF_HISTORY` 字段。
3. 读取端从同一已授权快照读取原列与对应证据，展示“来源原金额差异”，不将理论金额冒充原金额。
4. 若需要元数据保存，必须只允许同事务、同版本、原 sealed-origin 与经济字段完全未改的保留；源值修订、新审核和库存动作仍走各自规则。当前一般保留规则不足以宣称这点已实现。
5. 在独立授权的合成 PostgreSQL 目标上，验证接收→提交→重新连接读回、错误证据拒绝、完整回滚、并发/重放、权限和旧路径不回退。版本化目录/源码摘要审查通过前，不开放执行入口。

本轮明确保留执行阻断，而不是先放宽导入或审核再等待补证据。
