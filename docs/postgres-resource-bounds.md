# PostgreSQL resource-bound composition leaf

`adapters/postgres/src/bounded-pool.ts` is a lazy, explicit composition leaf for pinned `pg` 8.23.1. It is not a production factory, enabled API, deployment configuration, database migration, SQL retry engine or capacity benchmark. It does not install software, create an account, seed data, read `.env`, connect on construction, or mutate global PostgreSQL type parsers. All numeric values are technical operator settings, not user-approved business limits, P95 targets or an SLA. No defaults are supplied.

## Configuration and admission

The host must supply host, port, database, user, a nonempty password, and an explicit TLS choice. Only password authentication is supported here; there is no URI/ambient `PG*`/pgpass fallback or implicit localhost/database/role/password. TLS is either explicitly disabled for an authorized environment, or certificate-verified with `rejectUnauthorized: true` and an optional explicit CA. Do not put credentials in committed source, documentation or logs. Supply the authorized operator configuration through the future host's secret/configuration boundary.

Required settings:

- `max`: maximum wrapper leases plus unresolved driver acquisitions. The same maximum is passed to pg.
- `maxPendingAcquisitions`: maximum FIFO waiters, excluding those already charged to `max`; zero disables waiting. Excess admission fails immediately with `PG_POOL_OVERLOADED`.
- `acquisitionTimeoutMillis`: end-to-end deadline starting when `connect()` is called, including wrapper queue time. `connectionTimeoutMillis` separately configures pg's connection/pool-checkout deadline.
- `statementTimeoutMillis`, `lockTimeoutMillis`, `idleInTransactionTimeoutMillis`: positive finite PostgreSQL session startup settings. Safe explicit startup options also override ambient `PGOPTIONS`; explicit encoding, application name, SSL negotiation and non-replication mode avoid incidental ambient overrides.
- `queryTimeoutMillis`: finite pg client read/callback timeout, required to exceed the server statement timeout so a server timeout has a chance to arrive first. This ordering is not a network-delivery guarantee.
- `idlePoolTimeoutMillis`: finite retirement of unused pooled clients.
- `disposeGraceMillis` and `disposeTimeoutMillis`: graceful return interval (zero allowed), then a strictly later finite disposal deadline. All millisecond/count settings must be integers within the signed 32-bit timer/storage range; port must be 1–65535.

A caller deadline does not free an unresolved driver-acquisition slot. Late acquisition success is discarded with `release(true)`; late failure frees the charged slot. Thus repeated timeouts cannot launch unlimited hidden connection attempts. A client accepts one query at a time; concurrent queries are rejected rather than forming an unbounded pg client query queue. Existing adapters already await their queries sequentially.

## Cancellation, errors and disposal

An `AbortSignal` used by an existing read adapter still only stops callback work between its awaits. This leaf does not convert that signal into pg wire cancellation or claim that ignoring a late result stops SQL. PostgreSQL's statement/lock/idle-transaction settings are server-side protections. pg's `query_timeout` is a local response deadline, not proof of SQL cancellation or rollback. Non-SQLSTATE query failures, including pg read timeouts/transport errors, immediately retire the lease; SQLSTATE failures allow the existing adapter to request rollback, then the tainted connection is discarded on release. No query, command, transaction or COMMIT is retried automatically. A write/COMMIT error or forced disconnect can have an unknown outcome. Retain the original application request key and use the existing receipt/reconciliation contract rather than reissuing with a new key.

Lifecycle errors have stable `PostgresResourceError.code` values. Query errors retain only a recognized SQLSTATE code and, for current party-conflict translation, the fixed `customer_code_key`/`supplier_code_key` identifiers. Raw `message`/`where`, causes, SQL, parameters, connection targets and other driver fields are not retained or logged. Idle/checked-out client error events are handled; `backgroundFailureCount` gives the future host a non-sensitive counter to observe. An injected driver factory is a trusted synthetic-test seam, not support for an ambient-configured/native driver.

This is structural adapter compatibility, not preservation of the full pg error object. Current adapter error classification uses only the retained party SQLSTATE/constraint identities; recognized SQLSTATE errors still permit the adapter's rollback path. Genuine-engine diagnostic assertions need a separate trusted test-only raw-driver observation boundary: `tests/integration/proof.ts:15–16` validates the exact deferred transfer COMMIT error message and PostgreSQL `where` context, so that validator cannot run unchanged on errors returned through this bounded pool. Keep its exact assertions intact and observe the original driver error only inside the authorized isolated engine harness. Do not widen public error fields, publish raw provider diagnostics, or weaken the assertion to a generic SQLSTATE match.

Release is idempotent at the wrapper and calls raw release at most once. An error argument, prior query failure, or release during a query discards rather than returning a questionable client to the idle pool. Returning a lease makes future queries fail and rejects its local in-flight query; a late driver result cannot be delivered as success. If raw release throws, its outcome is uncertain: capacity stays quarantined and release is not retried.

`dispose()` synchronously stops admission, rejects queued/acquiring callers, invokes driver `end()` once, and returns the same promise on repeated calls. Existing leases may return during grace; retained leases are then discarded. In-flight/late acquisition cleanup remains attached even after the disposal deadline. If end fails or cleanup cannot be confirmed by the deadline, disposal rejects with `PG_DISPOSE_FAILED` or `PG_DISPOSE_TIMEOUT`, never reports successful teardown. A host must treat that as an unhealthy/unfinished shutdown, not start replacement work through the same pool. An arbitrary injected/broken driver, a blocked JavaScript event loop, or a broken network cannot be made to provide guaranteed physical socket/server termination by a promise deadline. Validate pg/socket retirement and server enforcement in an authorized isolated real database before production use.

## Future host wiring, not implemented here

A future trusted production factory should validate its explicit operator settings, construct exactly one owned `BoundedPostgresPool`, and inject that same object into the existing product/sales/transfer query readers and sales/transfer/authentication/party/import transaction adapters. The leaf structurally satisfies their existing `connect(): Promise<client>`, `query(text, values)` and `release(error?)` contracts. It does not supply authorization, credentials, account/admin creation, HTTP/listener startup or migrations. The future host must stop new requests before awaiting `dispose()` on shutdown, observe sanitized errors/counters, and must not translate an uncertain write timeout into “not committed.”

Synthetic verification: `node --test --test-concurrency=2 tests/postgres-bounded-pool.test.ts`. Tests use an injected event-emitting fake driver and fake timers, plus construction-only inspection of the installed pg client/pool. They cover overload, FIFO/queue deadlines, failed/late acquisition outcomes, release/disposal races and quarantine, query queue prevention, sanitized errors, no retry, ambient credentials, and unchanged global type parsers. These are not evidence of actual PostgreSQL timeout, lock, commit, cancellation, network or performance behavior. The existing read adapters' AbortSignal behavior is unchanged.
