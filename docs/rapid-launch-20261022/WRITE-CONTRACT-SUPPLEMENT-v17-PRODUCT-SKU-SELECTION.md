## 本次要确认的唯一完整建议

沿 Demo 原规格页的颜色多选、版型多选和一个尺码组，用户明确保存商品时，由服务器生成“选中颜色 × 选中版型 × 该商品所属组完整有效尺码”的组合。只新增不存在的真实组合。打开、选择、预览、取消、只读查询都不创建 SKU。

这是对现有“不生成笛卡尔矩阵”写合同的明确变更，不以 Demo 外观或 v11 旧批准替代确认。例如选中 2 个颜色、2 个版型、所属组 3 个尺码，会形成 12 个目标组合；已有 5 个则只新增缺少的 7 个。若不接受此生成范围，必须明确哪些组合算“实际要建”；现有三种选择本身无法表达任意稀疏组合，不能由开发者猜，也不能强塞回人工输入 SKU 编号的表格。

新商品 CREATE 使用本次明确选定组；编辑商品新增规格只使用服务器锁定的当前实际所属组。不把本候选扩大成已有 SKU 跨组搬迁、批量改组或全局尺码生成；改组关联规则继续原合同，冲突明确拒绝。

新补组合的 SKU UUID 由服务端原编号依赖分配。建议对本次普通商品维护新增的 SKU 明确扩展使用 `NJNEW-` 加该新 UUID 的 32 位小写字符，长度 38；称“新系统规格编号”。这是一项待确认的普通商品维护编号规则，不是复用已有批准。只给本次真实新增 SKU 赋号；旧编号逐字保留，不回填旧缺码，不生成条码、不按显示名绑定、不按顺序猜号。

## 原事务如何复用

仍使用原 `POST /api/products/v2/commands`、原 CREATE／EDIT、当前角色、原 requestKey、原商品 expectedVersion 和完整资料字段。仅拟在原命令增加明确的规格选择意图，表达选中颜色 ID、版型 ID；组身份沿原 `values.sizeGroupId`，编辑时同时核当前持久化归组。准确字段命名由 C 将本候选正式批准后与 F2 一次冻结；没有第二 API、浏览器发号或预留编号接口。

原 `skus` 对已有实际 SKU 的身份／版本／原编号处理保持；不要求 UI 为新组合先制造 `skuCode`。原显式实际 SKU 输入模式继续兼容，但同一命令不允许两种新增输入重复指定同一组合。选择缩减不删除、不停用原 SKU，已存在的停用组合不自动恢复；若需要重新启用，沿原明确维护操作另行表达。

先在原事务核当前权限和原键。原键成功重放返回原结果，不因字典成员后续变化重新生成；同键不同选择／资料仍冲突。锁当前商品和组成员，按实际 ID 与已有组合检查，在同一个 PRODUCT CREATE／EDIT 操作中新增全部缺少 SKU。已有组合复用原 ID／原编号，只有真实新增 SKU v1，并留存原 created_operation_id；商品本次有实际变更时版本只加 1，原审计／回执准确记新增事实。

继续原真实唯一约束：SKU UUID、sku_code、(product_id,color_id,fit_id,size_id)。唯一冲突、商品或 SKU 版本冲突、失效颜色／版型、组外尺码、超现有单商品 5000 SKU 技术边界、写入或延迟校验失败，整笔商品与 SKU／条码／同命令图片／审计／回执同提交同回滚；不部分成功、不静默截断、不覆盖旧身份、不重试换号。生成只建 SKU，不写库存、不造 0 库存、不增加 MAIN 条码；条码继续现有独立原始绑定规则。
